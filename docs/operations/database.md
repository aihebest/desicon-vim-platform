# Database: schema, migrations and security

The VIM platform stores its workflow data in **Azure SQL** (SQL Server in a
container on your machine). Every table lives in the `vim` schema. Entity
Framework Core ("EF Core") is the library that maps the C# classes to tables
and creates or changes those tables through **migrations**.

> **What is a migration?** A small C# file, generated by a tool, that
> describes one change to the database structure ("create table Cases",
> "add column InvoiceNumberKey"). Migrations are kept in Git, run in order, and the
> database records which ones it has already applied (in the table
> `vim.__EFMigrationsHistory`). That way every environment ends up with
> exactly the same structure.

## What is in the database

| Table | Purpose |
|---|---|
| `vim.Cases` | One row per invoice package (the `InvoiceCase` aggregate). Unique `Reference` (e.g. `VIM-2026-000123`), `RowVersion` for concurrency, `VendorNameKey` / `InvoiceNumberKey` for duplicate checks. |
| `vim.CaseDocuments` | Files attached to a case (the PDF itself is in Blob Storage; this row holds its path and SHA-256). |
| `vim.CaseChecklistAnswers` | Every checklist answer for every stage and resubmission round. |
| `vim.CaseFlags` | Warnings such as possible duplicate or bank-details mismatch. |
| `vim.AuditEvents` | **Insert-only** history with a hash chain. Unique on (`CaseId`, `Sequence`). |
| `vim.CategoryRoutes` | Which reviewer handles each invoice category (seeded on first start, then maintained in the workbench). |
| `vim.RouteChanges` | **Insert-only** record of every routing change: who changed which reviewer, when, old and new values. |
| `vim.OutboxMessages` | Notifications waiting to be emailed (sent by the `OutboxDispatch` function). |
| `vim.InboundMessages` | Emails already processed, so a retry never creates a second case. |
| Sequence `vim.CaseReferenceSeq` | Gives each new case its number. It never restarts, so references are unique across years. |

Enum values (status, channel, etc.) are stored as readable text such as
`UnderVerification`, so the tables make sense in a query tool and in Power BI.

### Why `VendorNameKey` and `InvoiceNumberKey` exist

Duplicate detection compares values after removing case, spaces and
punctuation: `"ABC Ltd."` = `"abc ltd"`, and `"INV-0012"` = `"inv 12"`. SQL
cannot run those C# rules, so the application calculates both keys every
time a case is saved and stores them in two indexed columns on `vim.Cases`.
The duplicate check first asks SQL for candidate cases with the same vendor
number, the same vendor-name key **or** the same invoice-number key (the
last one catches the same invoice resubmitted under a slightly different
vendor name), then the domain rules decide which candidates are real
duplicates.

## Creating the first migration (one-off, on your machine)

The repository does not yet contain migration files: they must be generated
with the real EF Core packages, which this repo's build agent could not
download. Do this once, in PowerShell, from the repository root
(the folder that contains `Desicon.Vim.sln`):

```powershell
# 1. Install the EF Core command-line tool (once per machine)
dotnet tool install --global dotnet-ef --version "10.0.*"
# If it is already installed, update it instead:
#   dotnet tool update --global dotnet-ef --version "10.0.*"

# 2. Restore packages and make sure everything builds
dotnet build

# 3. Generate the initial migration into src/Desicon.Vim.Infrastructure/Persistence/Migrations
dotnet ef migrations add InitialCreate `
  -p src/Desicon.Vim.Infrastructure `
  -s src/Desicon.Vim.Web `
  -o Persistence/Migrations
```

- `-p` (project) is where the migration files go: the Infrastructure project.
- `-s` (startup project) is the app the tool would normally start. You do not
  need a database or secrets for this step: the Infrastructure project
  contains `DesignTimeVimDbContextFactory`, which the tool uses instead of
  starting the web app.

Open the generated `..._InitialCreate.cs` and check it: you should see
`EnsureSchema("vim")`, the sequence `CaseReferenceSeq`, the nine tables and
the indexes listed above. Commit the whole `Persistence/Migrations` folder.

For every later model change, run the same command with a new descriptive
name, e.g. `dotnet ef migrations add AddVendorPortalTables ...`.

## Applying migrations

### On your machine (local SQL Server in Docker)

```powershell
# Type the local connection string once per PowerShell window (it is not saved to disk).
# Format: Server=localhost,1433;Database=VimDev;User Id=sa;<password from your .env>;TrustServerCertificate=True;Encrypt=True
$env:VIM_LOCAL_SQL = Read-Host "Local SQL connection string"

dotnet ef database update `
  -p src/Desicon.Vim.Infrastructure `
  -s src/Desicon.Vim.Web `
  --connection $env:VIM_LOCAL_SQL
```

### In Azure: migration bundle (what the pipeline does)

The running apps **never** change the database structure, and they do not
apply migrations at start-up. Migrations are applied by the deployment
pipeline (`.github/workflows/deploy.yml`) using a separate, more privileged
**migration identity**. The pipeline builds a *migration bundle*: a single
executable that contains every migration and applies whatever the target
database is missing.

To build and run a bundle yourself (for example to test it):

```powershell
# Build a self-contained bundle for Windows
dotnet ef migrations bundle `
  -p src/Desicon.Vim.Infrastructure `
  -s src/Desicon.Vim.Web `
  --self-contained -r win-x64 `
  -o .\out\efbundle.exe --force

# Apply it to a database (local example)
.\out\efbundle.exe --connection $env:VIM_LOCAL_SQL

# Apply it to Azure SQL with your own Entra sign-in (you must be allowed DDL on that database)
az login
.\out\efbundle.exe --connection "Server=tcp:<server>.database.windows.net,1433;Database=VimDb;Authentication=Active Directory Default;Encrypt=True"
```

If you prefer to review the exact SQL first (useful for production change
control), generate an idempotent script, which only applies the steps a
database is missing:

```powershell
dotnet ef migrations script --idempotent `
  -p src/Desicon.Vim.Infrastructure -s src/Desicon.Vim.Web `
  -o .\out\migrate.sql
```

## Security: audit history must be insert-only

The application only ever **adds** rows to `vim.AuditEvents` and
`vim.RouteChanges`. The database must enforce that too, so that not even a
bug or a compromised app can edit or erase history:

- The app identities (web and function app managed identities) are in a role
  that has **`DENY UPDATE, DELETE ON [vim].[AuditEvents]`** and
  **`DENY UPDATE, DELETE ON [vim].[RouteChanges]`**. A DENY always wins over
  a GRANT in SQL Server.
- This is applied by `infra/scripts/create-sql-users.sql`. Run it after the
  first migration has created the tables, and again after any migration that
  drops and recreates either table (dropping a table drops its permissions).
  **Check that the script includes `vim.RouteChanges`** (it was added after
  the script was first written).
- The foreign key from `AuditEvents` to `Cases` is `NO ACTION`, never
  `CASCADE`, so deleting a case cannot silently delete its history.
- Each event also carries a SHA-256 hash of the previous event. Changing or
  removing a row breaks the chain, which `AuditEvent.VerifyChain` detects.

Other points:

- **Production uses Managed Identity, not passwords.** The Azure connection
  string is `Authentication=Active Directory Default` with no user name or
  password. SQL logins with passwords (like `sa`) are for your local Docker
  container only.
- **Duplicate email processing:** `vim.InboundMessages.MessageId` (the
  immutable Microsoft Graph message id) is the primary key. If two intake runs
  ever process the same email at once, the database rejects the second insert
  and that run's whole save is rolled back, so no second case is created.
- **Concurrency:** `Cases.RowVersion` changes on every update. If two people
  act on the same case at once, the second save fails with the message
  "This case was changed by someone else. Reload and try again." Nothing is
  half-saved.
- **Transient faults:** the app retries automatically (up to 5 times) when
  Azure SQL briefly drops a connection, which is normal during maintenance.
